Why we built it

AI coding agents now write most of our code — and they say "done" when it isn't: tests skipped, gaps left silent, the spec quietly changed. When nobody can tell which parts were really checked, a company can't ship agent-written code. We hit this ourselves on Jul 3, 2026, when an agent overwrote a working screen and reported the fix complete. The harness started that day.

AI coding stops being a chat you trust and becomes a production line you can audit.

The builder never grades itself

Every step gets two audits by a model from another vendor. The runner — not the coding agent — calls the final audit and keeps the verdict.

Ship exactly what passed

Only the git tree that passed audit is committed. If one byte changes in between, nothing ships. A fourth failure stops for a human.

Mistakes don't repeat

195 recorded failures, each written as trigger · environment · break point · guard. Every new session reads them before it starts.

Cheap to run

About $0.57 per build session and $0.01 per rule audit, so every step can afford an independent review.

A system that learns every day

Every failure becomes a rule; every fix becomes a skill. 195 recorded failures and the approved skills are read by each new session — the system gets stricter every day. We are moving this memory onto a dedicated search server (Failure RAG · Success RAG).

Red-Sandwich Harness

Our core method, published as an open specification on GitHub. AI-generated code can pass a happy-path example while missing edge cases or drifting from the agreed spec. The harness wraps every build step between two deterministic gates and lets an adversarial reviewer attack it.

Top breadSpec-Lock TDD GateInput/output contracts are fixed before implementation; execution is blocked when they fail.
FillingAST Pure Units≤ 35 logic lines per function, ≤ 200 lines per file, cyclomatic complexity ≤ 5 — checked on every edit.
Bottom breadStrict IsolationFresh state per fold and per step; only the exact tree that passed audit is committed.
Red-Team Auditor

An independent model attacks the implementation with concrete counterexamples.

Missing values, extreme inputs, shape mismatches and leakage paths. Each finding is reproduced locally, then locked in as a test.

Only an explicit PASS from the executable gates admits the next stage — never the coding agent's own report.

Grown into the v6.6 deterministic harness

The sandwich now runs unattended across all our projects: one step per AI session, two separate audits, automatic retries.

  1. Spec & plan map
  2. Build (Claude Code)
  3. Lint gate (AST hooks)
  4. Rule audit (GPT)
  5. Final audit (GPT)
  6. Commit audited tree
  1. Spec: inputs, outputs and acceptance tests are fixed before any code.
  2. LLM session (Main): the Runner opens a fresh LLM session (Claude Code) and hands it the Step spec; it loads the skills it needs, pulls related records from Failure RAG and Skill RAG, and hooks check every save.
  3. Sub-LLMs: the Main session can spawn helper LLMs in parallel (reviewer, comparer, worker). They only return results; PASS/FAIL comes from the Runner and the audit LLMs.
  4. Machine checks: code size and complexity hooks run on every save.
  5. Audit LLM · Rule (GPT, a different vendor): checks the diff against the written rules.
  6. Audit request: the session only leaves a request file; the Runner reads it and calls the Audit LLM · Final (GPT, a different vendor).
  7. FAIL: Final audit sorts findings into Blockers and non-blockers. Blockers come back all at once, go into Failure RAG, Effort rises one level (low → medium → high) and a new session fixes them in one patch.
  8. Known issues: non-blockers do not stop the Step; they wait in Known issues, and a Defect analyst (subagent) groups them and links them to a later Step that touches the same file.
  9. PASS: only the audited tree is committed; some Steps also wait at the Human gate (Playtest) before the next Step starts.
  10. Milestone: Final audit (full) checks the whole milestone and clears the remaining Known issues in one consolidated patch.

Where we hit the wall

Everything above was built and run on a small home setup: one main desktop (RTX 3060 12 GB, i5-12400F, 32 GB RAM), a separate RAG server for failure and skill records (Ryzen 5 2400G, 8 GB RAM, 120 GB SSD + 2 × 4 TB HDD), and four monitors — three 24-inch on the main PC, one on the RAG server as a live status board. Code is fine; graphics are not. A lip-sync model alone needs ~11 GB, so heavy jobs queue one at a time through our own memory guard. With cloud GPUs and credits we would render full-length virtual-singer videos, batch seller videos, and generate 3D assets at full quality.
